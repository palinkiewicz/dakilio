# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dakilio is an open-source, privacy-first Android mood journal: a smaller alternative to Daylio. It uses Kotlin, Jetpack Compose and Material 3 Expressive. Package: `pl.dakil.dakilio`.

The app is past its proof-of-concept stage. `.materials/poc.md` was the original POC brief; it's kept only as history and is no longer the spec. Where it disagrees with the code or this file (its POC-only scope limits, user-defined mood counts), the code and this file win. `.materials/dakilio_early_stage_ideas.md` is background on *why* things are the way they are, not a backlog. `.materials/daylio_format.md` documents the `.daylio` backup format (reverse-engineered) and how it maps onto Dakilio; read it before working on the importer. `.materials/dakilio_format.md` specifies Dakilio's own `.dakilio` backup format.

## Commands

Machine-specific setup (JDK path, emulator) lives in `CLAUDE.local.md`, which is git-ignored and may not exist.

- Compile while iterating: `./gradlew :feature:<name>:impl:compileDebugKotlin` (or `:app:assembleDebug`).
- All unit tests: `./gradlew testDebugUnitTest :core:model:test :core:daylio:test :core:backup:test :core:security:test`. The JVM modules' task is `test`, not `testDebugUnitTest`.
- A single test class: `./gradlew :feature:timeline:impl:testDebugUnitTest --tests "pl.dakil.dakilio.feature.timeline.impl.TimelineBuilderTest"`.
- Lint: `./gradlew :app:lintDebug`.
- Versions: the release workflow passes the tag's version (`-Pdakilio.version=1.2.3`); local builds report the default from `app/build.gradle.kts`, so a local build of a release tag doesn't show that tag's version.
- Build types, which all install side by side:

  | Build type | App id | Launcher label | Notes |
  |---|---|---|---|
  | `assembleDebug` | `pl.dakil.dakilio.debug` | "Dakilio (DEBUG)" | — |
  | `assemblePreview` | `pl.dakil.dakilio.preview` | "Dakilio (PREVIEW)" | R8 like release, signed with the debug key. Use it to smoke-test minification. |
  | `assembleRelease` | `pl.dakil.dakilio` | "Dakilio" | Signed only when a `keystore.properties` exists; otherwise unsigned. |

  Labels come from the `appName` manifest placeholder in `app/build.gradle.kts`.
- Device verification:
  - Launch with `pl.dakil.dakilio.debug/pl.dakil.dakilio.MainActivity`.
  - Debug builds allow `run-as pl.dakil.dakilio.debug` (for example, `ls files/photos`).
- Asset pipelines (both are reproducible; don't hand-edit their outputs):
  - `python3 -I tools/fetch-icons.py` regenerates `core/designsystem/res/drawable/sym_*.xml` and the generated `DakilioSymbols.kt` from `tools/icons.txt`. To add an icon, add a line to `icons.txt` and re-run the script.
  - `tools/subset-font.sh` rebuilds the Google Sans Flex subset (axes `wght`, `ROND` and `wdth` 75–100).
- Baseline profile: `:app:generateBaselineProfile` times out under Gradle's runner on the emulator. Instead:
  1. Install `app-nonMinifiedRelease.apk` and the `baselineprofile` test APK.
  2. Run `adb shell am instrument -w -e targetAppId pl.dakil.dakilio pl.dakil.dakilio.baselineprofile/androidx.test.runner.AndroidJUnitRunner`.
  3. Copy the pulled profile into `app/src/main/generated/baselineProfiles/` as both `baseline-prof.txt` and `startup-prof.txt`.

## Build setup

- Uses AGP 9.5 with built-in Kotlin, so modules never apply `org.jetbrains.kotlin.android`. Also uses Kotlin 2.4, KSP 2.3, Hilt and Gradle 9.8.
- Convention plugins live in `build-logic/convention`: `dakilio.android.{application,library,feature,room}`, `dakilio.hilt` and `dakilio.jvm.library`. Shared Android/Kotlin config, Compose setup and opt-ins (Material 3 Expressive, shared transitions, …) are applied there. Change build config there, not in individual modules.
- `material3` is pinned to `1.5.0-beta02` in `gradle/libs.versions.toml`, ahead of the BOM, because the stable line hides the Expressive APIs (`MaterialExpressiveTheme`, `MaterialShapes`, `ButtonGroup`, flexible app bars, `ShortNavigationBar`, `SegmentedListItem`).
- `compose-stability.conf` marks `core.model` types and read-only collections as stable. Keep models immutable.
- Unit tests include Android resources (AGP's Compose Preview tasks require it), and `failOnNoDiscoveredTests` is off for modules without tests.
- Keep dependencies minimal. There is deliberately no network stack and no `INTERNET` permission. Coil is used without its network module. Icons come from bundled Material Symbols, not `material-icons-extended`. There are no chart or reorder libraries; charts are drawn with Canvas.

## Architecture

The layout follows NowInAndroid: `app` → `feature:*:impl` → `feature:*:api` / `core:*`.

- `core:model` (pure JVM): domain models, plus pure logic that has to be host-testable (`EntryValidation`, `Streaks`, the mood helpers `primaries()`/`byLevel()`).
- `core:database`: the Room schema, exported to `core/database/schemas/`.
  - **Every schema change needs a migration.** Bump `version` in `DakilioDatabase` and add the step: an `AutoMigration(from, to)` where Room can infer it (new tables or columns; add a spec for renames and deletions), otherwise a hand-written `Migration` in `Migrations.kt`, listed in `ALL_MIGRATIONS`. Installs, including the released 1.0.0, must keep their data, so never edit a schema in place or fall back to a destructive migration. This applies between releases too: teammates' debug installs are real databases.
  - Versions: 1 is the released 1.0.0; 2 (released in 1.2.0) added the diary and habit reminder columns; 3 added the `reminder` table. `MIGRATION_1_2` is hand-written and checks for existing columns, because those columns first landed by editing version 1 in place, so some development databases already had them. `MIGRATION_2_3` is hand-written too: it copies the reminders that were on into the new table. The old `reminder_on`/`reminder_minute` columns stay in `diary` and `habit`, unused (`legacyReminder*` in the entities), because dropping a column on minSdk 29's SQLite means rebuilding tables that others reference.
  - There's no `MigrationTestHelper` test (it needs a device). To check a migration: build the APK of the last release tag (a `git worktree` at the tag), install it, add data, then install the new build over it.
  - Never edit an exported `<n>.json` once that version has shipped or been committed. Auto-migrations are generated from those files, and the build writes the new version's file.
  - Data the new schema needs for existing rows is filled in by the migration itself, or lazily by the app.
  - `DefaultData` seeds everything inside `RoomDatabase.Callback.onCreate`: the 5 primary moods (ids 1..5 = their level), the "Your Journey" diary, tag groups and, in debug and preview builds only, 12 **sample entries with photos**.
  - The samples (entries, their strings and the photos under `assets/sample/`) live in `core:samples`, which binds the optional `SampleData`. Only `:app`'s debug, preview and `nonMinifiedRelease` (baseline profile) variants depend on it, so release APKs carry none of it and start empty.
  - Sample posts use the reserved ids `DefaultData.SAMPLE_POST_IDS` (1..12). Removal relies on those ids. The seed moves the post id sequence past the range even without samples, and SQLite `AUTOINCREMENT` never reuses ids, so user posts can't collide with them. The sample UI (the More hint, Settings → Starter content) shows only while samples exist.
- `core:data`: repository interfaces and `Local*` implementations, bound in `DataModule`. Feature modules see only models and these interfaces, never entities or DAOs. `PostRepository.posts` is a single `Flow<List<Post>>`. Timeline, search and insights all derive from it in memory on the Default dispatcher; there is no Paging and no FTS.
- `core:daylio` (pure JVM, host-tested): reads `.daylio` backups (`DaylioArchive`), converts note HTML to text (`daylioHtmlToText`), maps tag icons from Daylio icon ids or label keywords (`daylioTagIcon`) and maps a backup onto Dakilio's model (`planImport` → `ImportPlan`). Uses kotlinx-serialization-json.
- `core:backup` (pure JVM, host-tested): the `.dakilio` format. It holds the JSON model (`DakilioBackup`), password encryption (`BackupCrypto`, `EncryptingOutputStream`), the archive reader and writer (`DakilioArchive`, `writeBackup`), `detectBackupKind` and `planRestore` → `RestorePlan`.
- `core:security` (pure JVM, host-tested): the app lock's logic. It holds passcode hashing (`PasscodeHasher`, PBKDF2 with the iteration count stored in each hash), `PasscodeRules`, `LockoutPolicy` (waits after failed tries) and `AutoLockPolicy` (when coming back locks again).
- `core:autobackup`: the automatic backup job (`AutoBackupScheduler`, `AutoBackupJobService`, `AutoBackupSync`). Only `:app` depends on it; the screen talks to `AutoBackupRepository` (core:data).
- `core:notifications`: diary and habit reminders (`ReminderScheduler`, `ReminderNotifier`, the two receivers, `ReminderSync`, `ReminderLaunches`) and their texts. Only `:app` depends on it; features edit reminders through `ReminderRepository`.
- `core:datastore`: user preferences only (theme, the tag limit, the last-used diary of the editor, the timeline's chosen diary, the sample-hint flag, tag style, beginner hints, entry text sizes, timeline view options, close after saving, the first day of the week, the photo size). User content lives in Room. The app lock lives in its own DataStore file (`LockDataSource`, `@LockStore`), and so do automatic backups (`AutoBackupDataSource`, `@AutoBackupStore`).
- `core:designsystem`: the theme, the Google Sans Flex typography (rounded `ROND` axis for display and headline styles; `FittingText` narrows a one-line label on the `wdth` axis before cutting it off, used by `ConnectedToggleRow`), shapes, the symbols (bundled icons and letters), haptics, `MorphShape`/`PolygonShape`, and generic expressive primitives.
- `core:ui`: domain-aware components (`MoodBadge`, `PostCard`, diary selectors, `IconPicker`, `PhotoViewer`, the delete dialogs, `SuggestedGroupCard`, `DaylioBackupCard`, `SwitchListItem`), formatters, `NavTransitions`, and `Modifier.sharedContainer`.
- `core:navigation`: Navigation 3 with **one back stack per bottom-bar tab** (`NavigationState` and `Navigator`). Back from another tab's root returns to the Timeline tab. The entries of each stack are decorated separately so state and ViewModels survive tab switches.
- Feature `api` modules contain only `@Serializable` NavKeys. `impl` modules expose `EntryProviderScope<NavKey>.xxxEntry(navigator)`, which `app/ui/DakilioApp.kt` wires up. A feature may depend only on other features' `api` modules.
- ViewModels use `hiltViewModel()`. Keyed screens (the entry editor and the diary editor) use Hilt assisted injection with their NavKey.

### Non-obvious decisions

- **Moods: a fixed 5-level scale with aliases** (like Daylio). The level count is a constant (`MOOD_LEVELS`), deliberately not configurable: a variable scale would break per-level charts, the validated palette and `.daylio` import.
  - Each level has exactly one primary mood (`is_primary`), which can be renamed but never removed, plus any number of aliases: other names for the same level ("Sad" next to "Bad").
  - Entries point at the exact mood, so they keep the chosen name. Analytics and the search filter group by `level`; `Mood.value` is computed as `(level - 1) / 4` for averages.
  - Deleting an alias with no entries just deletes it. With entries, the user either **archives** it (`is_archived`: hidden from pickers, old entries keep it) or **replaces** it (its entries move to another mood, then it's deleted). `post.mood_id` is `ON DELETE RESTRICT`, so a mood is never deleted under entries.
  - Picking: a level with aliases shows a dot (`MoodBadge(hasAliases)`). In the editors, the first tap on a face selects the level's primary, and tapping the selected face again opens `MoodAliasOverlay` (core:ui), a dimmed full-screen stack of that level's moods. The rules are the pure `moodTap()` in `MoodPicking.kt`. The wizard doesn't auto-advance on a first tap of a level with aliases. The timeline's check-in card has nothing selected yet, so it opens the overlay on the first tap.
  - Deselecting: a level without aliases clears when its selected face is tapped again. Inside the overlay, tapping the current mood keeps it, and an explicit clear button after the faces deselects.
  - Customization lives in `feature:moods` (More → Moods).
- **Mood visuals belong to the level.** `MoodVisuals.kt` holds one rest/active MaterialShapes polygon pair and face curvature per level, plus the per-level *light-mode* mark color. Aliases share their level's face. Dark-mode tones are derived in OKLCH at runtime (`deriveAccentColors`).
  - The default palette (crimson, orange, periwinkle, green, teal) is a diverging scale that was validated for colour-vision-deficiency separation in both themes.
  - **Mood colors** work like tag colors: `mood.color_key` stores a `TagColor` palette key. `Mood.colorKey` is the mood's own color; `Mood.color` is the one it shows (own, else its level primary's), resolved in the data layer (`MoodDao.observePrimaryColors()`, also for entries' moods). With no color at all, `moodColors()` falls back to the level's built-in color (`levelColors()`). The seed sets no colors, so a fresh install shows the validated palette.
  - Colors are picked in More → Moods: the edit dialog (name, then a `ColorRow` with "Level color" for a primary or "Use “…” color" for an alias) shows a live face preview.
  - Don't swap it for a red→yellow→green ramp: yellow and green collapse for protanopes.
- **Deleting a tag** first counts its entries (`TagRepository.tagUsage`). An unused tag is just deleted. A used one offers:
  - **archive** (`is_archived`, with an Undo snackbar): old entries keep showing it, while pickers and the customization screen hide it;
  - **delete** for good: it's removed from every entry, and entries left with nothing at all (no mood, text, photos or other tags) are deleted too, since the editor never saves an empty entry. The dialog states both counts.
- **Deleting a tag group** follows the same rules (`TagRepository.groupUsage`). A group none of whose tags are used is just deleted. A used one offers **archive** (with an Undo snackbar) or **delete** for good, which deletes its tags, removes them from every entry and deletes entries left with nothing but tags from that group.
- **Extras** are optional tools that build on the core features. They're the first section of the More screen (there's no Extras sub-screen), so their settings don't crowd the Tags, Moods or Diaries screens. There are three: Habits, Keywords and Reminders.
  - An extra has **no on/off toggle**: its state is the switch. One that holds nothing is simply unused, and its row says "Not used yet" instead of showing a count.
  - Each extra is its own feature module with its own screen; More depends only on its `api` module. Adding one: a new module, one `MoreItem` in More's Extras section (plus its status in `MoreViewModel`) and one `xxxEntry` in `DakilioApp`.
- **Symbols** (core:designsystem `icon/`): a tag's or diary's icon is a `DakilioSymbol`, a sealed type with two kinds. `DakilioIcon` draws both, so screens never tell them apart.
  - `VectorSymbol` is a bundled Material Symbol (the generated `DakilioSymbols`). Its key is the symbol's name.
  - `GlyphSymbol` is text, **a letter in either case**, drawn in the bundled Google Sans Flex (`GlyphIcon`), so letters add no drawables to the APK. Its key is `glyph:` plus the text (`glyph:A`, `glyph:ł`). It's resolved by that rule, not from a list, so any key of 1–2 visible characters draws; a key that's neither kind falls back to the label icon. A new kind of symbol takes a new `kind:` prefix, which no Material Symbol name can contain.
  - Drawing (`GlyphMetrics`, tuned next to the Material Symbols): type at 84 % of the box, the rounded axis, Medium weight (stems as thick as the icons' 2 dp strokes) and Bold for `filled`. Capitals are centered and every letter shares their baseline, like centered text, so "a" sits lower than "A" and a letter lines up with the label next to it; ink that would leave the box (Ż, a deep descender) is pushed back in, and text too wide is set smaller (`glyphTopLeft`, `glyphFontSizeToFit`, tested). The size ignores the user's font scale.
  - `IconPicker` (core:ui) has two pages, Icons and Letters, each a list of `SymbolSection`s (`iconSections`, `letterSections()`), and opens on the page and section of the current symbol. The letters come from the string resources `symbol_letters_upper`/`symbol_letters_lower`, so each language brings its own alphabet (Polish adds ą, ł, ż, …) and a letter picked in one language still draws in another. The font subset covers Latin and Latin Extended-A; a language outside it needs `tools/subset-font.sh` widened first.
- **Tag colors** are part of More → Tags (`feature:tags`, not an extra): a default color per tag group, which a tag can override.
  - On the Tags screen, each group card's color button (a dot of the group color, or a palette icon) opens `GroupColorSheet`, which applies a pick at once with a live preview of the group's tags. A tag's own color is a "Color" row in the tag editor sheet ("Use group color", then the palette), saved with the tag. The sheet lives in `TagColorPicker.kt`; the swatches, `ColorDot` and `ColorRow` are shared with the Moods screen from core:ui `ColorSwatches.kt`. The tag chips on the Tags screen show their resolved color.
  - The seed groups (and so the suggested groups) come with a default color each, chosen to fit their meaning and to be the palette's most distinct six: Emotions pink, People orange, Activities violet, Health green, Journey brown, Weather sky (`DefaultData.Group.colorKey`). The suggestion cards show their tags in it.
  - `tag.color_key` and `tag_group.color_key` store a palette key from `TagColor` (core:ui), never a color value, so the palette can be retuned without a migration. Never rename a key; unknown keys mean no color.
  - `Tag.colorKey` is the tag's own color; `Tag.color` is the one it shows (own, else its group's), resolved in the data layer, also for entries' tags (`PostRepository.posts` combines with `TagDao.observeGroupColors()`).
  - The tones come from `deriveAccentColors` (core:ui `color/AccentColors.kt`), which the mood colors use too. Read-only `TagPill`s use the `soft`/`accent` tones. The editor colors only a **selected** tag's fill; unselected tags stay neutral so selection stays the strongest signal in the grid.
- **The Tags screen** (More → Tags) shows tags in the user's tag style (`UserSettings.tagStyle`), like the editor: the icon grid shares `TagIconGridLayout` (core:ui) with the editor's picker.
  - **Reorder mode** (the app bar's swap action) turns every group into a card with its tags as a vertical list, each with a drag handle. Groups move among groups; tags move only within their group (moving one to another group stays in the tag editor sheet). TalkBack gets "Move up/down" actions instead.
  - Drags change a draft in `TagsViewModel` (`reorderDraft`), so they never fight Room's re-emissions; each drop saves `position` (`TagRepository.reorderGroups`/`reorderTags`, positions 0..n-1 of the active items; archived ones keep theirs, and ties are fine since everything orders by `position, id`). It needed no schema change.
  - The drag itself is the library-free helper in core:ui `Reorderable.kt` (`rememberReorderState`, `Modifier.reorderableItem`, `Modifier.dragHandle`, `ReorderScrollArea` for edge autoscroll). It works for lazy items and plain Columns. An item swaps once its leading edge passes a neighbour's middle (`swapDirection`, tested), not its center: a list clamped to its items (tags in a group card) can't push the held item past the end item's center. In a `LazyColumn`, pin the scroll position by index on each move (`requestScrollToItem`), or the list jumps when its first visible item swaps.
- **Habits** (`feature:habits`), an extra: a habit is one tag (unique per tag) plus a target of days per week. Its name is the tag's label.
  - Entries of **every diary** count, and a day counts once however many entries carry the tag. Weeks start on the user's first day of the week (see below), the same as the Insights heatmap. The pure logic lives in `core:model` `Habit.kt` and is tested.
  - `habit.tag_id` is `ON DELETE CASCADE`, so deleting a tag or its group, the intro's group pruning and a Daylio import remove its habit too.
  - **The progress popup:** `EntryEditorViewModel.save()` reads `HabitRepository.weekCounts` for the entry's week before and after saving. `Habits.bumps` keeps the habits whose count went up, so a day already counted never bumps again, and edits count as well as new entries. The bumps go into the `HabitProgressEvents` singleton (a `StateFlow`, so they survive the editor closing). `HabitProgressHost`, placed once in `DakilioApp` above the nav bar, shows them as a self-dismissing card: the old count, then a tick up with a "+1", a filling segment and haptics.
- **Keywords** (`feature:keywords`), an extra: words attached to a tag (`tag_keyword`, `ON DELETE CASCADE` like habits) that suggest it when they show up in an entry's title or note. The pure logic is `Keywords` in `core:model` `Keyword.kt` (tested), which also holds `foldForSearch()`, shared with search.
  - **Matching:** words are compared folded (case, accents, ł). A keyword matches whole words by default; `approximate` makes its last word also match longer words starting with it ("rower" → "rowerem"), which handles Polish inflection without matching "runway" for "run". A keyword may be a phrase (consecutive words).
  - **Not intrusive:** `EntryEditorViewModel` watches the text fields with `snapshotFlow` and matches `Keywords.settledText()` at once, which leaves out the word still being typed, then the full text after `KEYWORD_SETTLE_MS` of no typing. So a suggestion appears on a space or a pause, never for a half-typed word.
  - **Editor:** `KeywordSuggestions` ("From your note") sits right under the note field in the wizard's note step and in edit mode, never in read mode. By default it offers chips (tap adds, ✕ dismisses). With `UserSettings.keywordAutoAdd` (a choice on the Keywords screen) a newly matched tag is ticked at once and shown as a filled chip that a tap undoes. Words already in the saved text never auto-add, so opening an old entry changes nothing. Dismissing, undoing or unticking a matched tag puts it in `EditorForm.dismissedKeywordTags` for that session. A fresh match (not in the saved text, not yet announced this session) also gives a gentle tick and a brief `KeywordToastHost` pill at the bottom (above the wizard's bar or the keyboard) for 2.5 s: the tag chip, plus Undo in auto-add mode, or a tap to add in suggest mode. Matches arriving while it's up join it and restart its timer.
  - **Older entries:** only an existing tag's keyword sheet looks through older entries, and only while it's open (`KeywordsViewModel.queryPast`/`pastPreview`, debounced, on the words as edited). It shows how many mention the words but lack the tag (`Keywords.pastMatches`); "Review entries" opens `KeywordPastScreen` (`KeywordPastKey`, carrying the words as edited), which lists them newest first under month headers as short excerpts around the match (`Keywords.matchRanges` + `keywordExcerpt`, highlighted) with the mood face. Nothing is ticked at first; a tap on a row opens the entry, the checkbox opts it in, and the tag is added to the ticked ones behind a confirmation. The list is fixed when the screen opens, so an entry tagged meanwhile stays as "already tagged". Nothing is offered after saving or on the list, since tagging old entries is often unwanted.
  - In a `.dakilio` backup, keywords are nested in their tag (`BackupTag.keywords`).
- **The Archived screen** (More → Archived, `feature:archive`) lists archived mood aliases, archived tag groups (with all their tags) and archived tags of active groups. Each can be restored or deleted for good; an archived alias with entries can only be deleted by replacing it. Restoring a tag whose group is archived restores the group too. The delete dialogs (`DeleteTagDialog`, `DeleteGroupDialog`, `DeleteAliasDialog`, `ReplaceAliasDialog`) live in `core:ui` so the Tags, Moods and Archived screens share them.
- **Every entry is in exactly one diary** (`post.diary_id`, `ON DELETE RESTRICT`). The editor picks it with the single-select `DiarySelector` (the same dropdown as the timeline's diary filter, first in the date and time row) and remembers the last one (`UserSettings.lastEntryDiaryId`). The timeline's diary filter persists too (`UserSettings.timelineDiaryId`, `null` = all; a deleted diary falls back to all, and a Daylio import resets it).
- **Deleting a diary** is blocked for the last remaining diary. Its entries are either moved to another diary or deleted together with their photo files.
- **Two editor layouts.** New entries go through the mood → tags → note step wizard. Existing entries open `EntryOverview`, a single page that starts **read-only** for reading: the chosen mood, chips of every selected tag (archived ones included) and the note as plain selectable text, with empty sections and an empty title left out. The app bar's Edit button (in place of Save) switches the whole page into edit mode for that session: one row of mood faces, the tags (folded into chips of every selected tag until Expand or a tap on the chips unfolds the groups for that session), the note fields, date/time chips and the diary selector. Saving there closes the entry, unless Settings → Close after saving (`UserSettings.closeAfterSave`, default on) is off: then the page goes back to read mode with the saved state as the new baseline, and Back leaves. Edit mode lives in `EditorForm.editing`. Both share `EntryEditorViewModel`, `tagGroupItems` and `NoteFields`.
- **Diaries suggest tag groups.** In the editor, groups suggested by the entry's diary are expanded; the rest are collapsed under "More groups". When none are suggested, all groups are expanded.
  - Every group in the editor is a collapsible panel (`TagPicker.kt`). What the user folds open or shut lasts only for that editor session (`toggledGroups` in `EntryEditorScreen`).
  - The tag style is a user setting (`UserSettings.tagStyle`): a Daylio-style icon grid (the default) or chips. Read-only tag displays (post cards, search) always use chips.
- **Daylio import replaces everything** (More → Import from Daylio, `feature:importer`). It doesn't merge: after a warning and a confirmation, every entry, photo, diary, tag group, tag and mood alias is deleted, and the backup goes into a fresh "Your Journey" diary.
  - The swap is one transaction (`ImportDao.replaceAll`). Photos are copied (re-encoded through `PhotoRepository.importBytes`) before it, and they're deleted again if it fails.
  - The 5 primaries are kept and renamed: a renamed Daylio base mood keeps its name, the others get the seed names. Daylio's custom moods become aliases; archived ones only if entries use them.
  - Daylio stores no archived state for groups, so a group whose tags are all archived is imported as an archived group.
  - `sqlite_sequence` is never reset, so imported entries can't take the reserved sample ids.
  - Daylio names its assets `/assets/...`, which Android 14+ `ZipFile` rejects by default. `allowRootedZipEntries()` installs a `ZipPathValidator` that allows the leading slash but still rejects `..`.
  - Voice notes and favourites are skipped and counted in the preview.
  - **Getting the file in:** the invisible `BackupReceiverActivity` accepts `SEND` and `VIEW` of `.daylio` files and forwards the URI (with the read grant) to `MainActivity` (`singleTask`) in Dakilio's own task. The filters are deliberately not on `MainActivity`: Daylio's backup screen shares in a way that makes Android ignore `singleTask` and start a second copy inside Daylio's task. The filters mirror Daylio's own manifest: the types `application/daylio` and `application/octet-stream` (Android doesn't know the extension), plus `.daylio` path patterns for "Open with". Daylio itself registers no `SEND` target. `MainActivity` drops the URI into the `IncomingBackups` singleton. While a file is waiting, `DakilioApp` opens More → Import, and `DaylioImportViewModel` takes the file, unless an import is already running. When Daylio is installed (a `<queries>` entry in core:ui's manifest; `rememberDaylioInstalled()`/`openDaylioBackup()` live in core:ui), the Pick step offers a shortcut (`DaylioBackupCard`) to Daylio's `BackupAdvancedActivity`, falling back to its launcher screen.
- **Dakilio backups** (More → Backup & restore, `feature:backup`, format in `.materials/dakilio_format.md`):
  - A backup is a ZIP with a readable `dakilio.json` first, plus `photos/`. With a password, the whole ZIP is wrapped in streamed AES-256-GCM chunks behind a readable header. The key comes from PBKDF2; only JDK crypto is used.
  - It holds everything, settings included. A restore **replaces everything**, like the Daylio import, through the same `ImportDao.replaceAll` (which takes several diaries, primary colors, suggested groups and habits).
  - `IncomingBackups` (core:data) sniffs a shared or opened file's first bytes: `.dakilio` files go to the Backup screen, anything else to the Daylio importer. Files picked in the intro's import step take the same route (`IncomingBackups.deliver(uri)`).
  - Bump `FORMAT_VERSION` only for changes that old apps can't safely ignore; new optional fields don't need it.
  - `BackupWriter` (core:data) builds and writes a backup for both the manual export and automatic backups.
- **Automatic backups** (the first section of Backup & restore; off until a folder is picked). A `.dakilio` file is written into a folder the user picks (`OpenDocumentTree`, persisted grant), so another app can sync it off the phone. **Battery comes first:**
  - One periodic framework `JobScheduler` job (no WorkManager, no alarm, no wakelock, no foreground service): daily (24 h, 8 h flex) or weekly, persisted, never on low battery or low storage, and by default only while charging (a switch). `AutoBackupScheduler` reschedules only when the wanted `JobInfo` differs from the pending one, since scheduling again restarts the period. Never change `JOB_ID`.
  - **A run skips when nothing changed:** `AutoBackup.fingerprint` (core:backup) hashes the backup JSON without `exportedAt`/`appVersion` plus every photo's name and size; when it matches the last success and an automatic backup is still in the folder, the run ends after one DB read. Back up now and the first backup after picking a folder always write.
  - Files are named `dakilio-auto-yyyy-MM-dd-HHmm.dakilio`. Only names `AutoBackup.parseFileName` accepts are ever deleted (`filesToDelete`, the newest `keep` stay), and only after a new backup is complete, so the user's own files and the last good backup are safe. A failed write deletes its half-written file.
  - The optional password is stored encrypted by a Keystore key without user authentication (`BackupPasswordVault`), since the job runs with the phone locked. If the key is gone, runs fail with `PasswordUnavailable` until it's set again.
  - The `autobackup` DataStore file is excluded from device-to-device transfer (`data_extraction_rules.xml`): the folder grant and the Keystore key don't move, so a new phone starts with automatic backups off.
  - `AutoBackupSync` (started by `MainActivity` after the intro, like `ReminderSync`) keeps the job in step with the settings. The screen shows the status (overdue after twice the interval plus a day, `AutoBackup.isOverdue`) and the newest automatic backups to restore; More's Backup row shows a problem in the error color.
  - To test: `adb shell cmd jobscheduler run -f pl.dakil.dakilio.debug 4201` runs the job now; `adb shell dumpsys battery unplug` / `set ac 1` / `reset` simulates the charger.
- **Export** (`feature:export`, More → Export, the first row of the Data section): the journal as a PDF or Markdown, to read rather than restore, filtered by period and diaries, oldest first.
  - Markdown is rendered by the pure `renderMarkdown` (tested), with the localized labels built by the screen (`ExportLabels`). With photos it's a ZIP of `journal.md` and `photos/`.
  - The PDF is drawn by `PdfJournalWriter` on the framework `PdfDocument` (A4, Google Sans Flex through font variation settings): day headings that stay with their first entry, the level's mood face (`moodGlyph`, `moodColors(mood, dark = false)`), tags as soft pills, notes split across pages line by line (`linesThatFit`, tested) and photos decoded at about 900 px.
- **First-run intro** (`feature:intro`, hosted by `app/ui/IntroFlow.kt` in its own Nav3 back stack instead of `DakilioApp`): language → import → tag groups.
  - **Nothing may open the database before the language step is done**, because `DefaultData.seed` writes localized names on first open. That's why `sweepOrphans()` skips a database that doesn't exist yet. The step lists `AppLanguages` (core:ui `AppLanguage.kt`) and applies a pick with the framework `LocaleManager`, which recreates the activity; the intro's back stack survives it. Per-app languages need Android 13, so older versions only show the device-resolved language.
  - The groups step shows `DefaultData.suggestedGroups()` (the seed groups, read from resources without the DB), all ticked. "Get started" calls `OnboardingRepository.keepStarterGroups`, which deletes the unpicked seed groups by their fixed ids with the usual delete-for-good rule (their tags leave the sample entries).
  - The import step (`IntroImportKey`) offers both ways in, side by side: a Dakilio backup, and Daylio (with `DaylioBackupCard` when Daylio is installed). Either pick button hands the file to `IncomingBackups`, which routes it by content, so a file picked under the "wrong" card still lands on the right screen. That screen is pushed onto the intro's stack: the Daylio import (`DaylioImportKey`) or the backup screen in restore-only mode (`BackupKey`, `restoreOnly = true`: no Create card, and Back leaves the screen). A finished import or restore ends the intro. A file shared or opened at any point during the intro is routed the same way (`DakilioApp`'s More routing isn't composed yet).
  - `OnboardingRepository.shouldShowIntro()`: not if finished (`intro_done`); yes if it was left halfway (`intro_started`); otherwise only if the database doesn't exist yet, so installs from before the intro never see it (its group step would delete their groups).
  - The same suggestions are offered later in More → Tags (an app bar action and the empty state, `SuggestedGroupsSheet`). One counts as added while an active group has its name, and adding inserts a new group with fresh ids.
- **Photos** come through the system Photo Picker, so no permission is needed. `LocalPhotoRepository.import` re-encodes each image as JPEG at quality 80, which strips EXIF (including GPS), into `filesDir/photos`.
  - **Size:** Settings → Scale down photos to (`UserSettings.photoSize`, `PhotoSize`: 640/960/**1280**/1600/2048 px on the long edge, or Original) sets the scaling. The pure sizing is `PhotoSizing` in core:model `Photo.kt` (tested). Original still caps at about 16.8 MP (`MAX_ORIGINAL_PIXELS`) so a 200 MP photo can't run out of memory. A restore uses its backup's own size; a Daylio import uses the current one.
  - **Knowing which photos are too large:** `PhotoRepository.countLargerThan` reads each used photo's size from its JPEG header (`BitmapFactory` bounds only, no pixel decoding) the first time it's asked, then keeps the sizes in memory for the app's run. Every write in the repository (import, shrink, delete, sweep) updates them, so later visits to Settings touch no files. No size is stored in the database.
  - **Scaling down existing photos:** when some are larger than the setting, Settings offers "Scale down N larger photos" behind a one-way confirmation. `PhotoRepository.shrinkAll` runs in the app scope (leaving Settings doesn't stop it) and rewrites each file under the same name through a temp file and an atomic move, so no entry changes and a crash leaves every photo whole.
  - Files imported during an editor session are deleted if the draft is abandoned.
  - `sweepOrphans()` runs at startup.
- **Post time** is stored as an epoch timestamp plus `utc_offset_min` and a `local_date` epoch day, so an entry stays on the day it was written even across time zones.
- **The timeline layout** is a pure function, `buildTimeline()`, with unit tests. It covers:
  - day headers;
  - today's check-in card;
  - "No entries" rows;
  - runs of 3 or more empty days collapsed into an expandable quiet stretch;
  - "Also this day" chips for entries in other diaries, only under days that have entries in the selected diary (and today);
  - days with entries only in other diaries are compact empty rows (and can join quiet stretches), with a small read-only `DiaryHint` of those diaries' icons.
- **Timeline view options** live in a menu (`TimelineViewMenu`) that grows out of the tune button in the timeline's app bar: preview size (`PreviewLength`: 4/8/16 note lines or full), compact icon-only tags, the tag limit (`TagLimit`, a slider: 0–10 or all before a "+N" pill, stored as the number or "All", old names `Three`/`Six`/`Twelve` still read; with no stored value it's 10 in compact mode, otherwise 6), the month navigator (on by default) and the timeline text size, which is the same preference as Settings → Entry text size. They reach every `PostCard` (timeline and search) through `LocalEntryDisplay`, provided in `MainActivity`. In search, a note whose first match is past its start is shown as an excerpt from just before it (the pure `noteExcerpt()`).
- **The timeline's app bar** has two layouts. With one diary and the month navigator not in the app bar, it's the `LargeFlexibleTopAppBar`: the greeting collapses into the bar's title, with the date and streak as its subtitle. With more than one diary, or the month navigator in the app bar (`hasHeaderControls`), a pinned `TopAppBar` holds `TimelineHeaderControls` in its title slot: the `DiaryFilterDropdown` (core:ui; as wide as its label, up to the room left) and the app-bar month navigator. Only that bar turns `surfaceContainer` on scroll; the greeting with the date and streak is the list's first row (`headerCount` shifts list indices by one), so it scrolls away under the bar. When both pickers show (`hasBothPickers`), the month may be compacted (short month over its year) and search moves from the app bar to a FAB above the new-entry FAB. Insights still uses the chip row `DiaryFilterRow`.
- **The month navigator** (`MonthNavigator.kt`): `▲ month ▼` (`UserSettings.monthNavigator`; it reaches the screen through `TimelineUiState.Ready`, not `LocalEntryDisplay`, since only the timeline uses it). By default it's a floating pill (`FloatingMonthNavigator`, round buttons) under the app bar, hidden only while the big greeting shows (the large bar not collapsed, or the greeting row in view); `UserSettings.monthNavigatorInAppBar` (a sub-switch in the view menu) puts it in the app bar instead, with no background of its own, taking all the width the diary dropdown leaves (the dropdown is as wide as its label, up to what the narrowest navigator leaves). Its label is one line, and stacks the short month over its year next to the diary dropdown only when one line doesn't fit.
  - The label follows the first row not covered by the pill (in the app bar, the first visible row). On the pill it keeps the width of the year's widest month, so the arrows sit right next to it and don't move; in the app bar it fills the room between the arrows.
  - Every jump lands on the **top** of a month (its divider, or the first timeline row for the newest month, so the greeting is gone), just below the pill or the app bar, and scrolls at once (`jumpToMonth`); unlike day jumps it never waits for a new list or opens quiet stretches.
  - ▲/▼ step through `sectionMonths()`, the months with a section of their own. A month swallowed whole by a quiet stretch that began in a newer month has no section, so the arrows skip it and the picker lands on that stretch (`monthTopIndex`). The helpers are pure and tested in `TimelineBuilderTest`.
  - Tapping the label opens `MonthPickerSheet`: a year switcher over a 4×3 grid, each month with a dot of its average mood level's color (`monthSummaries`), dimmed without entries in the filter, disabled outside the timeline's range.
- **Entry peek** (core:ui `EntryPeek.kt`): holding any `PostCard` (Timeline and Search) shows the whole entry large over the blurred app, until the finger lifts. `EntryPeekHost` wraps `DakilioApp`'s content and provides `LocalEntryPeek`; without it `Modifier.entryPeek` does nothing.
  - After the long press, the detector consumes every change on `PointerEventPass.Initial`, so the card's own clickable doesn't fire on release and the list doesn't scroll. The overlay is in the same window on purpose: a dialog or popup window can't take over a touch stream that's already in progress.
  - Scrolling while holding: dragging up reads further, with a gain (`peekScrollGain`, max 3×) that lets one sweep reach the end of a medium note. Very long notes keep scrolling while the finger rests in the top or bottom 12 % (`edgeScrollSpeed`). The edge zones only work after the finger has moved. Both are pure and tested.
  - Blur needs API 31+ (`RenderEffect`); older versions get a stronger scrim only.
  - **Share:** a chip under the card. It can't be tapped (the peek owns the gesture): sliding onto it (a slightly larger target) ticks, grows and fills it, and pauses scrolling and the edge zones; letting go there shares the entry as an image. The card's content is `EntryPeekContent`, shared with the image.
  - The image (`EntryShare.kt`) is rendered off-screen as soon as the finger reaches the chip: `EntryShareRenderer` lays the whole entry out at unbounded height, 1080 px wide (a 360 dp layout), and records it into a `GraphicsLayer` that's never drawn, after loading the photos through Coil, so none is caught half loaded. Entries taller than `MAX_SHARE_HEIGHT_PX` are drawn at a smaller density (`shareDensity`, tested). There's no search highlight, and a small "Dakilio" footer.
  - It's written to `cacheDir/shared/` (cleared each time; JPEG with photos, PNG without) and shared through core:ui's `${applicationId}.share` FileProvider. The chooser is launched through an ActivityResult launcher, so the app lock treats it like a picker and coming back doesn't lock.
- **Search** (`feature:search`) has one filter model, `SearchFilters` (`PostSearch.kt`, pure and tested): text, mood levels, tags (any/all), diaries, a `Period`, weekdays and `Has` (photos, text, long note). Every way into a filter sets those same fields, so all of them show and can be edited in the facet bar (Mood · Tags · Diary · When · Has, each with a live sheet in `FilterSheets.kt`):
  - Before anything is typed, `SearchIdle` offers recent searches, **lenses** (`Lenses.kt`: presets such as On this day, Bright days or Tough days, hidden when they find nothing; Shuffle opens a random entry over a month old) and the frequent or forgotten tags.
  - Text matches only the title and note, never tag names, so a word that is also a tag doesn't flood the results. Instead, the word being typed offers matching tags as chips under the facet bar (`typedWord()`); picking one replaces the word with a tag filter.
  - Typing `#…` swaps the facet bar for matching tags; picking one removes the word and adds a tag filter. With results, "Narrow down" offers the most common tags that would actually narrow them.
  - Period presets stay relative (`Last7Days`, `OnThisDay`, …) so a saved search keeps its meaning.
  - **Recent searches** stay on the device (`SearchHistoryDataSource`, max 8). Core stores them as opaque strings; search encodes `SearchFilters` as JSON, and unreadable entries or missing tags and diaries are dropped when they're read. A search is saved on the IME Search action and when a result is opened, but not when it's only a lens.
- **Insights** follow the `dataviz` skill's rules: stat tiles, a stacked bar with 2dp gaps, legends that carry the mood faces, and single-hue bars. `InsightsCalculator` is pure and tested. Streaks ignore the selected range.
- **The first day of the week** is a setting (`UserSettings.weekStart`: `Region`, the default, or Monday, Saturday or Sunday). `Region` follows the **device** locale (`Resources.getSystem()`, not the per-app language), which also carries Android 14's regional first-day preference. `SettingsRepository.firstDayOfWeek` gives it resolved; the UI reads `LocalFirstDayOfWeek` (core:ui, provided in `MainActivity`). Habits (`Habits.weekStart(date, firstDay)`), the Insights heatmap, search's weekday toggles and the facet label follow it. The M3 date pickers take theirs from the locale and can't be told.
- **Dates use the app's language** (`ui_format_language`, which each translation sets) combined with the device region, so they never mix with untranslated UI.
- **Container transforms:** the FAB and the post cards grow into the editor, and the timeline's search button (an app bar action, or a FAB when both pickers show) grows into Search. This works through `sharedContainer(key)` together with `NavTransitions.sharedContainer` entry metadata. Tabs use a fade-through transition (`NavTransitions.topLevel`).
- **App lock** (More → App lock, `feature:lock`): a PIN (4–12 digits) or a password, with optional biometrics on top. It's a gate for the UI, **not encryption**: the database stays unencrypted in Android's app sandbox, and the screen says so.
  - **Session state** is the `AppLock` singleton (core:data). A cold start with the lock on starts locked; `MainActivity` reports `onStop`/`onStart` (not configuration changes), and `AutoLockPolicy` decides with `elapsedRealtime` and the user's delay (immediately … 15 minutes).
  - **The app's own pickers don't lock it:** `MainActivity.startActivityForResult` (which every ActivityResult launch goes through) calls `AppLock.expectReturnFromPicker()`, so a return within 10 minutes stays unlocked. Plain `startActivity` launches count as leaving.
  - **`LockGate`** wraps `IntroFlow`/`DakilioApp` in `MainActivity`. While locked the app stays composed underneath (navigation, ViewModels and an unsaved draft survive), hidden from accessibility and covered by `LockScreen`; Back moves the task to the back instead of reaching it. The first frame waits until the lock state is known. Screens composed under the gate must not act on lock state meant for the lock screen.
  - **Storage:** settings, salted PBKDF2 hashes of the credential and the recovery answer, and the failure count live in the separate `lock` DataStore. It's never part of a `.dakilio` backup, so a restore can't lock anyone out. Device-to-device transfer keeps it.
  - **Lockout:** 5 tries, then waits of 30 s, 1 min, 5 min and 15 min, persisted (a restart doesn't reset them; a clock set back gets the longest wait). PIN and recovery-answer failures share the count.
  - **Biometrics** use the framework `android.hardware.biometrics.BiometricPrompt` (`BiometricAuth`), so there's no androidx.biometric dependency and `MainActivity` stays a `ComponentActivity`; it needs the normal `USE_BIOMETRIC` permission. **Standard** (the default) accepts Class 2 sensors. **Strong** wraps the prompt around a Keystore key that needs Class 3 biometrics and is invalidated by a newly enrolled biometric: biometric unlock then turns itself off, and the lock screen explains why until the next PIN unlock. Labels come in whole phrases per sensor type, since "Unlock with %s" can't be declined in Polish.
  - **Recovery** is the user's pick of one: none (the default; clearing the app's data is the only way back in), the phone's screen lock (`DEVICE_CREDENTIAL`), or their own question, whose answer is normalized (case, spacing) and hashed. A recovery unlocks with `AppLock.recovered` set, and `DakilioApp` opens More → App lock to choose a new credential without the old one.
  - Changing anything on the App lock screen asks for the current credential first (biometrics accepted). "Hide screen content" (`FLAG_SECURE`) works with the lock off too.
- **Reminders** (`feature:reminders`), an extra, with the schedule in `core:notifications` and the pure planner `Reminders` in core:model `Reminder.kt` (tested). Every reminder lives on the one Reminders screen; the diary editor and the habit sheet have no reminder settings.
  - **A reminder** (`reminder` table, `ReminderEntity`) is about exactly one diary (`diary_id`) or habit (`habit_id`), both `ON DELETE CASCADE`, at a `minute` of the day on chosen weekdays (`days`, a bit per day, Monday first: `ReminderDays.toMask`; 127 = every day), with an `enabled` switch. A diary or habit can have any number of them. Nothing is seeded, so there's no intro step and no permission dialog at startup.
  - **The screen** follows Habits: a list of reminders by time (the time large, the diary's or habit's icon and name, the days summary, a switch), a "New reminder" FAB and `ReminderSheet`: Diary/Habit, then the diary or habit as chips, the time (M3 `TimePickerDialog`), the days (core:ui `WeekdayToggles`, shared with search; at least one stays on) and a live summary sentence. Delete has an Undo snackbar.
  - **Rules:** a reminder comes only on its weekdays. A diary reminder is skipped on a day that diary already has an entry. A habit reminder comes until the week's target is met, then rests until the next week (its first allowed weekday from the user's first day of the week).
  - **One alarm, no services:** `ReminderScheduler` keeps a single `AlarmManager` alarm at the earliest reminder still to come. It's `setExactAndAllowWhileIdle` when exact alarms are allowed (`SCHEDULE_EXACT_ALARM`, the user's "Alarms & reminders" switch on Android 12+, off by default on 14+; always allowed below 12), otherwise the inexact `setAndAllowWhileIdle`, which can come up to an hour late (on Android 10–11 much later). While a reminder is on and exact timing isn't allowed, the Reminders screen ends with a tip that opens the setting; granting it sends a broadcast the reschedule receiver turns into an exact alarm. A second tip, while the app is under battery optimization (`PowerManager.isIgnoringBatteryOptimizations`), opens the app's system page (`ACTION_APPLICATION_DETAILS_SETTINGS`): stock Android delivers the alarm anyway, but some makers' battery savers stop apps in the background, and that page holds both the battery setting and any autostart switch. The tips are `ReminderAccess` state, refreshed on resume. The time comes from `Reminders.next`, which looks up to 14 days ahead. `ReminderAlarmReceiver` re-reads the data, shows what still applies (`Reminders.due`), then sets off at once any later reminder the alarm already passed (`Reminders.missed`), so a reminder a minute later still comes. A late alarm that slipped past midnight still shows within `Reminders.LATE_GRACE` (3 h), checked against its own day's entries (`ReminderRepository.snapshot(date)`); later than that it's dropped. There's no WorkManager. The receiver isn't exported, so `am broadcast` from the shell can't trigger it; to test, set a reminder a couple of minutes ahead.
  - **Staying in step:** `ReminderSync`, started by `MainActivity` once `DakilioApp` is composed (never during the intro: the database mustn't be created early), watches Room's invalidation tracker (`TableChanges`) on reminder, diary, habit, tag, post and post_tag plus the first day of the week, and replans. That covers every write path (the screen, entry saves, cascades, import, restore) without hooks. Replanning also takes down notifications that no longer apply.
  - `ReminderRescheduleReceiver` (boot, app update, clock and time zone changes) is **disabled in the manifest** and enabled only while some reminder is on. Zones are read fresh (`ZoneId.systemDefault()`), since the injected `Clock` keeps the zone it was made with.
  - **Permission:** the Reminders screen asks for `POST_NOTIFICATIONS` (Android 13+, `ReminderAccess`) only when a reminder is added or switched on, and saves it either way. While some reminder is on and notifications can't show (denied, off in the system, or the user turned off that kind's channel), a banner at the top says which and opens the app's or that channel's system settings.
  - **Notifications:** one channel each for diaries and habits (ids in core:data `ReminderChannels`, since the screen checks them; never rename one), created once a reminder is on rather than at the first notification, so they show in the system settings early; one notification per diary or habit (tag `diary`/`habit` with the entity id), however many reminders it has, so two at the same moment show once. They're `VISIBILITY_PRIVATE` with a generic public version, so names stay off the lock screen. A tap opens MainActivity with extras; `ReminderLaunches` → `DakilioApp` opens a new entry in that diary, or with the habit's tag ticked (`EntryEditorKey.presetTagIds`).
  - **Habits:** deleting a habit cascades to its reminders, so the Habits screen's Undo reads them first (`ReminderRepository.forHabit`) and adds them back under the habit's new id.
  - **Texts:** `string-array`s `reminder_diary_texts`/`reminder_habit_texts` in core:notifications. Each language writes its own lines in its own voice, and **the counts may differ** (`tools:ignore="InconsistentArrays"`). Don't translate them line by line. `Reminders.textIndex` walks through them day by day.
  - In backups, reminders are nested in their diary or habit: `reminders: [{ enabled, time: "HH:mm", days: ["mon", …] }]` (no `days` = every day). 1.2.0's single `reminder` is still read when it was on.
- **Privacy:** `data_extraction_rules.xml` excludes everything from cloud backup but allows device-to-device transfer, except the automatic backup setup.

## Conventions

- All user-visible text goes in each module's `res/values/strings.xml`, including seed data.
- Translations: English and Polish (`values-pl`). A new string needs its Polish version too, with all four plural quantities (`one`, `few`, `many`, `other`). Polish uses „…” quotes, lowercase "ty" forms and avoids gendered past tense addressed to the user. Adding a language: a `values-xx` per module, `localeFilters` in `app/build.gradle.kts`, `app/src/main/res/xml/locales_config.xml` and `AppLanguages`. Settings → Language opens the system per-app language screen (Android 13+).
- Use Material 3 Expressive throughout:
  - spring motion through `MaterialTheme.motionScheme`;
  - shape morphing on selection or press (`pressScale`, `MorphShape`);
  - segmented groups (`SegmentedShapes`, `segmentedItemColors()`);
  - `raisedToggleColors()` for toggles on container-colored backgrounds;
  - haptics through `rememberHaptics()`.
- **No endless decorative animation** (`rememberInfiniteTransition`, `infiniteRepeatable`, perpetual spins or pulses). It keeps the display at full refresh rate and stops LTPO screens from dropping to 1 Hz. Motion should be a short, settling response to a state change or input. Loading indicators are the only exception, because they disappear once the content is ready.
- **Beginner hints:** any line that teaches how to use the UI (as opposed to describing state) goes through `Hint { }` or `hintOrNull()` from `core/ui/Hints.kt`, so the "Show beginner hints" setting (`UserSettings.showHints`, provided as `LocalShowHints` in `MainActivity`) covers it.
  - Never hints: empty states, counts, validation, dialog warnings, setting descriptions, placeholders and screen taglines.
  - Layouts must look right without the hint: put spacing on the neighbours, not on the hint.
- Use `DakilioIcon(DakilioSymbols.X, filled = selected)` for icons. Tags and diaries store symbol keys, which `symbolForKey()` resolves to a `DakilioSymbol`: a bundled icon or a letter (see "Symbols" above). Pass that to `DakilioIcon` or `ShapedIcon`; never read a drawable from it.
- Keep new logic Android-free where possible so it can be host-tested. The existing tests cover the timeline builder, the insights calculator, search, search excerpts, streaks, habits, the reminder planner, keyword matching, entry validation, the Daylio reader and planner, the backup format (crypto, archive and restore planner), automatic backup rules, the Markdown export and PDF page layout, and the app lock's policies and hashing.
